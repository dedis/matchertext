\section{Evaluation}
\label{sec:eval}

To ground the matchertext discipline in evidence rather than argument,
we evaluate it on a large corpus of real-world code.
The evaluation treats every string literal and comment in the corpus
as a candidate embedded string,
and answers four questions that source code can answer directly:
\begin{itemize}
\item[\textbf{Q1}] How matchertext-compliant is existing code? (\cref{sec:eval:compliance})
\item[\textbf{Q2}] Which embedded languages carry the violations? (\cref{sec:eval:where})
\item[\textbf{Q3}] How much escaping would matchertext remove? (\cref{sec:eval:reduction})
\item[\textbf{Q4}] How deeply does embedding nest in practice? (\cref{sec:eval:nesting})
\end{itemize}
\Cref{sec:eval:open} discusses the questions the corpus cannot answer.


\subsection{Methodology}
\label{sec:eval:methodology}

The analysis extracts embedded text directly from each language's
own lexical structure rather than from ad-hoc pattern matching.
For C and C++ it uses the Clang lexer~\cite{lattner04llvm,llvm26clang},
recognizing all string-literal forms (including the wide, UTF-8,
UTF-16, UTF-32, and raw variants) and both comment styles;
for the remaining languages it uses
in-process tree-sitter grammars~\cite{brunsfeld26treesitter}.
Both paths emit string-literal and comment samples
that feed the same metric computation.
Each candidate string is further classified by content --
\eg as a URI, regular expression, HTML, SQL, or shell fragment --
using deterministic structural detectors backed by
a trigram naive-Bayes model,
with an explicit \emph{Unknown} bucket for samples too short or ambiguous
to label safely.
The compliance and escaping metrics below
do not depend on this classification,
which affects only the per-category attribution of results.
On held-out Linguist snippets, naive Bayes labels 4.7\%, 84\% correctly; detector accuracy is unmeasured.

The corpus is drawn from GitHub
and is intended to represent mature, widely-deployed production code:
every non-archived repository of \dataOrgs organizations
behind operating-system kernels, databases, browsers,
language toolchains, and similar infrastructure.
It comprises \dataRepos repositories and roughly \dataFiles source files
(on the order of 1.5~TiB of code),
yielding approximately \dataStrSamples string-literal samples
and \dataDocSamples comment samples.
JavaScript alone contributes about \dataJsStrSamples string samples,
reflecting both its prevalence and its string-heavy style.

The key metrics are as follows.
A sample is \emph{matchertext-compliant}
when its ASCII matchers match (\cref{sec:design}),
and the \emph{compliance rate} is the fraction of compliant samples;
a \emph{strict} rule treats a wrong-kind closer (\eg \verb|)| closing \verb|[|)
as a violation, while a \emph{relaxed} rule permits it.
A \emph{violation} is one unmatched or wrong-kind matcher.
A \emph{toothpick} is a single backslash character in a sample,
following the term ``leaning toothpick syndrome'' of \cref{sec:bg}.
To estimate the escaping that matchertext would remove,
each compliant string literal is rewritten
as the equivalent escapeless C++ raw string literal \verb|R"(|$\dots$\verb|)"|
(same toothpicks as \verb|M"(|$\dots$\verb|)"|)
\xxx{not quite exactly the same toothpicks!
	there will be a difference for unmatched matchers
	and for the raw-string closer sequence.}
and the surviving backslashes are counted,
yielding a \emph{toothpick reduction}.
The rewrite decodes every escape, \verb|\x5B| included,
and drops its backslash unless it decodes to one
or to a control other than tab, LF, or CR, which is kept verbatim.
An escape that cannot be written raw, such as a non-UTF-8 byte, keeps its backslash too,
as does every escape of a literal whose decoded content is not matchertext.
Binary-data literals (BinaryData and PseudoBinaryData,
such as file headers, test vectors, or terminal codes) are out of scope:
they are not readable text, writing their byte escapes raw would break the encoding,
and their brackets are byte values, not delimiters.
They count only toward sample and toothpick totals.
Finally, \emph{nesting depth} is the deepest matcher nesting a sample reaches;
\emph{raw} depth also counts unclosed openers.


\subsection{Q1: Compliance of existing code}
\label{sec:eval:compliance}

Existing code is already highly matchertext-compliant
at the level of individual embedded fragments.
As \cref{tab:eval:compliance} shows,
\dataStrCompliance of in-scope string-literal samples
and \dataDocCompliance of comment samples are compliant as written.
Per file, counting all its literals and comments, compliance is lower, \dataFileCompliance,
because one violating fragment makes the whole file non-compliant,
so per-sample-rare violations still touch a noticeable fraction of files.
The relaxed rule barely changes any of these figures
(file compliance rises only to \dataFileComplianceRelaxed,
comments to \dataDocComplianceRelaxed),
which means almost all violations are genuinely unmatched matchers
rather than correctly-paired-but-wrong-kind nesting.
Compliance is also high across every host language,
with string-literal compliance staying within a narrow band
from \dataHostComplianceMin for the least-compliant language up to \dataHostComplianceMax,
so no language in the corpus is broadly non-compliant.

\subsection{Q2: Where violations concentrate}
\label{sec:eval:where}

Violations are far from evenly spread across embedded-language categories.
As \cref{tab:eval:categories} shows,
regular expressions and shell fragments
carry \dataRegexViolations and \dataShellViolations violations respectively,
despite making up only \dataRegexShare and \dataShellShare of classified samples;
relative to their sample counts they are
far more often non-compliant than prose or identifiers.
CSS is similarly disproportionate,
contributing \dataCssViolations violations from only \dataCssSamples samples.
By contrast, identifier-like tokens and URLs
are essentially violation-free.
The pattern is that unmatched matchers cluster
in exactly the categories whose syntax routinely uses brackets singly,
rather than in the bulk categories
(plain prose, identifiers, file paths)
that dominate the sample count.

This is the pain point we anticipate
in \cref{sec:embed:c}:
printing and parsing code that emits or matches
lone, unmatched matchers within string literals --
\eg \verb|print("[")| or \verb|case "]"| --
is where the matchertext discipline bites.
Resolving the data by host language separates two effects.
The first is the per-sample violation \emph{rate}:
the bracket-single-use categories are most violation-prone
wherever they appear, and acutely in JavaScript,
where regular expressions average \dataJsRegexRate violations per sample,
shell fragments \dataJsShellRate, and CSS \dataJsCssRate.
The second is absolute \emph{contribution}, which is partly volume-driven:
in C++ and Java the single largest source of violations
is ordinary prose (\dataCppProseViolationShare and \dataJavaProseViolationShare of each language's violations),
not because prose is error-prone --
its rate is only about \dataProseRate{} --
but because prose strings are so numerous.
The category leading a host's violations thus differs by host,
but the categories intrinsically most likely to violate
are consistent across hosts.

Most string literals are not cross-language embeddings at all:
plain prose, identifier-like tokens, and file paths
account for about \dataBulkShare of classified samples (\cref{tab:eval:categories}).
Among the languages that motivate our injection discussion,
SQL accounts for \dataSqlShare, JSON for \dataJsonShare,
CSS for \dataCssShare, and XML for \dataXmlShare.
Because the corpus is infrastructure-heavy (\cref{sec:eval:methodology}),
these figures likely understate web-facing combinations
such as SQL in application code or HTML templating.
The classification is content-based and best-effort,
so its finer categories are approximate,
and it shows what is embedded, not why.

\subsection{Q3: Escape reduction}
\label{sec:eval:reduction}

The central benefit of matchertext is the escaping it removes.
Rewriting each compliant string literal
as an equivalent C++ raw string literal
eliminates \dataReduction of the in-scope toothpicks,
cutting them
from about \dataScopeToothpicks to about \dataToothpicksConverted.
Escaped binary data, out of scope, holds another \dataBinaryToothpicks.
The host's raw-string form could hold \dataRawHoldableShare of the compliant literals,
and only a matchertext literal the other \dataMtOnlyShare (\eg C and Java lack raw strings);
both counts include literals without escapes.
As a concrete case,
the compliant C++ regular-expression literal
\verb|"\\b,\"axis\":(\\d+)\\b"|
carries eight toothpicks;
rewritten verbatim as the matchertext literal
\verb|M"(\b,"axis":(\d+)\b)"|,
the two quote escapes and three doubled backslashes vanish
and only the three genuine backslash escapes remain --
a 62.5\% reduction in that one literal.

The reduction is large but content-dependent.
Across the \dataOrgs organizations it ranges
from \dataOrgReductionMin to \dataOrgReductionMax,
with half of them between \dataOrgReductionQOne and \dataOrgReductionQThree.
As \cref{tab:eval:hostlang} (\cref{app:hostlang}) shows, it also varies by host language:
C-family languages and Java
see most of their toothpicks eliminated
(C \dataHostCReduction, C++ \dataHostCppReduction, Java \dataHostJavaReduction),
while others reduce much less,
most strikingly Go (\dataHostGoReduction), Python (\dataHostPythonReduction),
and TypeScript (\dataHostTypeScriptReduction).

A notable finding is that compliance and escape relief
are largely \emph{independent},
turning on where a language's escaping actually lives.
TypeScript is the clearest case:
its string literals are \dataHostTypeScriptCompliance compliant,
among the highest in the corpus,
yet rewriting them removes only \dataHostTypeScriptReduction of their toothpicks,
among the lowest.
The reason is that most of its backslashes (\dataTsRegexToothpickShare)
sit in regular expressions,
whose own escapes, like the three in the example above,
survive the rewriting.
A language can therefore satisfy the matchertext rule almost everywhere
and still gain little from raw-string rewriting:
the cost of becoming compliant
and the benefit of doing so are distinct quantities.


\subsection{Q4: Nested embedding}
\label{sec:eval:nesting}

Most bracket nesting is shallow.
Most samples contain no matchers at all,
and depth falls off sharply beyond one:
the average per-sample maximum depth
is only \dataStrAvgDepth for string literals
and \dataDocAvgDepth for comments.
Deep nesting does occur in a heavy tail --
the single deepest string sample reaches a raw depth of \dataStrMaxDepth,
in \dataStrMaxDepthHost (though that literal's deepest \emph{matched} nesting is at most \dataStrMaxDepthValidBound),
followed by maxima in JavaScript (\dataHostJavaScriptMaxDepth), C\# (\dataHostCSharpMaxDepth),
and Python (\dataHostPythonMaxDepth) --
but such cases are vanishingly rare.
Comments nest more on average than string literals,
consistent with comments containing structured examples and prose,
whereas string literals more often hold a single flat fragment.
For reference, \cref{app:nesting} plots the full depth distribution.


\subsection{Discussion and open questions}
\label{sec:eval:open}

The results suggest that the adoption cost is small
and the benefit could be large.
Over \dataStrComplianceFloor of string literals and over \dataDocComplianceFloor of comments need no change,
and rewriting the compliant majority
as raw string literals or matchertext literals
would remove \dataReduction of the in-scope toothpicks.
The remaining violations fall where \cref{sec:embed} predicts,
in syntaxes that use brackets singly,
and the near-identical strict and relaxed comment rates suggest that
they are lone matchers, the case the escapes of \cref{tab:unmatched-matchers} address,
rather than closers of the wrong kind.
Two questions from \cref{sec:intro} remain open:
how matchertext affects usability in common embedding tasks,
such as editing HTTP or SQL queries,
and how it affects the rate of syntax-related and security-related bugs,
which a static corpus analysis cannot measure.
Nor is the corpus a random sample: it counts forks and vendored, generated, or minified files
without deduplication, so widely copied code weighs more.
