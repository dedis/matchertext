# Simulated PLDI review: compiler and language implementation perspective

**Scope.** Review of `doc/main.tex` and every included section and appendix in the frozen snapshot `/tmp/matchertext-review-20261108`, identified by the review coordinator as commit `c81714bc3f74d3c2d0863f0153d401a879fa1267`. This is the Matchertext paper, not the separate injection-research paper. Source references below are relative to that snapshot and use its line numbers. I read the paper before inspecting the targeted artifact. I did not read other reviews, delegate, build, run experiments, or install dependencies. No project-specific `AGENTS.md` was found in the snapshot or working project by the searches performed; the supplied Matchertext project instruction applies. This is an advisory simulation, not an official venue rubric or decision.

## Assessment recorded before inspecting the artifact

The paper proposes an appealing division of responsibility: a guest promises a very small, language-independent structural invariant; a host offers an opaque region delimited using that invariant. With all three ASCII bracket pairs balanced, the host can locate the end without parsing the guest or interpreting its escapes. The host can gain this facility without requiring legacy host programs to obey the invariant globally. The guest can often remain within its existing language by using numeric escapes for unmatched punctuation. MinML explores a language designed around the discipline rather than adding one quoting construct.

My provisional paper-only assessment was **weak reject, with a plausible route toward borderline/accept through substantially better implementation evidence and evaluation semantics**. Confidence: medium-high in the practical compiler concerns, medium in the overall PLDI judgment. The core theorem is intentionally elementary; that is acceptable if the language-design and engineering payoff is established convincingly. At present the strongest claims concern cross-language convenience and low adoption cost, while the evidence mainly counts fragments. Neither Scheme reader support nor a new markup syntax establishes that the proposed C-like extension survives a mature compiler pipeline and its surrounding tools.

The largest paper-only uncertainty was the word “equivalent” in the escape-reduction experiment. A compliant source spelling is not necessarily a compliant decoded value; some values cannot appear literally in a language's source encoding; and ordinary raw strings already obtain much of the proposed escape relief. I also wanted a precise account of preprocessing, import/tag contexts, formatters, incremental editing, and error recovery. These concerns precede the artifact observations below.

## What is strong and worth preserving

1. **A useful, narrow interface between languages.** Separating hosting from being embeddable (`doc/host.tex:4`, `doc/embed.tex:4`) makes incremental adoption conceivable. A language can add opaque literals without breaking all old comments and string constants. This is a better deployment argument than requiring universal source conformance first.
2. **The exact-match condition matters.** Unlike a delimiter chosen to avoid accidental collisions, the proposed invariant permits a fixed embedding hole for every valid guest. The distinction from “there exists a delimiter for this particular string” is clear and meaningful.
3. **Reasonable design restraint.** Excluding angle brackets avoids imposing balancing on inequalities. Restricting sensitivity to ASCII punctuation keeps the lexical contract small. Related work acknowledges Dyck languages and Wyvern instead of claiming the underlying parsing fact is new.
4. **Useful empirical scale and candid limits.** The corpus exposes rare but consequential cases and reports host-language variation, a large Unknown classification bucket, and the dominance of non-language strings. The paper explicitly leaves usability and bug-rate effects open (`doc/eval.tex:326`). Those limits should remain explicit.
5. **A real language/tooling experiment.** The inspected MinML implementation and language-server work are considerably more substantial than a grammar sketch. The formalization supports the compositional argument; it does not need to be inflated into the main technical novelty.

## Three most consequential concerns

### 1. The escape-reduction claim lacks a consistent semantic contract

**Exact paper locations:** `doc/eval.tex:59` defines every backslash as a toothpick; `doc/eval.tex:62`–`doc/eval.tex:69` describes an equivalent raw-literal rewrite; `doc/eval.tex:316`–`doc/eval.tex:321` uses that result to infer adoption benefit. The same headline propagates to the abstract and conclusion.

**Paper-only concern.** “Compliant” can refer to the source spelling, decoded string value, or rewritten source. These are different objects. For example, the C literal `"\x5B"` has matchertext-compliant body spelling but denotes a single unmatched `[`. A pure matchertext literal cannot preserve that value while retaining the proposed contract. A literal containing `\r` raises a different issue: the value is balanced, but source newline processing or explicit character restrictions can prevent literal preservation. The paper needs to distinguish these cases from genuinely removable host escaping.

**Artifact-supported finding: demonstrated definition mismatch, unmeasured numerical effect.** `LLVM/src/RawRewrite.cpp:131`–`136` deliberately keeps numeric/name escapes as written and excludes their backslashes from the count. `LLVM/src/Parser.cpp:518`–`525` subtracts `encodingBackslashes` from the measured baseline. Thus the current implementation does not implement the stated “every backslash” definition. Leaving `\x41` literally inside a raw string also produces the four characters `\x41`, not the original value `A`; this is not an equivalent raw-literal conversion. Some control escapes are retained in the counter rather than emitted as a literal value. The counter is a useful selective escape-accounting model, but should be called that.

This is not evidence that the particular published aggregate was generated by this exact code, nor that its correct replacement must be larger or smaller. The snapshot's producer version and reported-number provenance need to be established. It is evidence that the paper and current artifact disagree on what the number means.

An encouraging cross-check is `go/toolchain/mrewrite/main.go:10`–`14` and `:138`–`154`: the actual rewriter refuses encoding/control escapes and checks the decoded value before emitting an `M` literal. Its executable transformation is appropriately more conservative than the synthetic headline estimate.

**Consequence.** The 94.78% headline cannot currently bear the interpretation “these escapes can be removed by a semantics-preserving migration.” Binary-like strings are sufficiently important in the reported result that the distinction cannot be relegated to a tiny caveat. It also obscures whether matchertext adds value beyond familiar raw strings.

**Concrete repair.** Define a small representation pipeline: source spelling → language-specific value → representability check → candidate literal spelling → decoded candidate value. Report (a) every source backslash, (b) backslashes used for host quoting/escaping rather than numeric data representation, (c) the subset of values actually expressible verbatim as matchertext, and (d) reduction after a checked conversion of that subset. Keep an idealized or selective metric if useful, with an accurate name and denominator. Retain `\x5B`, `\x41`, `\r`, invalid UTF-8 byte data, escaped backslashes, and embedded `)"` as explanatory examples. Compare default raw delimiters and adaptive raw delimiters separately from matchertext.

**Acceptance criterion.** A reader can reproduce each metric by hand on those examples, and an emitted migration preserves byte/code-unit values, types, and relevant literal semantics. The headline, tables, and artifact agree on exclusions and denominators. A small stratified audit against actual language decoders is more valuable than another order of magnitude of corpus size.

### 2. Compiler integration is described as a grammar problem when the hard boundary is earlier and broader

**Exact paper locations:** `doc/host.tex:111`–`114` promises verbatim content and reversal of early translations; `doc/host.tex:153`–`163` discusses universal character acceptance; `doc/appendix/grammar.tex:4`–`13` says realization reduces to conservativity; `doc/appendix/grammar.tex:60`–`70` gives language compatibility examples. `doc/design.tex:288`–`289` dismisses encoding as immaterial.

**Paper-only concern.** Conservativity is necessary, but it is not the single implementation requirement. A literal may have to survive source decoding, early Unicode escape translation, newline normalization, preprocessing token formation, macro expansion, and downstream APIs that unquote strings outside normal constant evaluation. The promise that Java Unicode escapes are disabled inside a new literal requires recognizing the opaque region before or during a translation step that presently precedes tokenization. This is feasible as a design change, but a post-translation grammar cannot establish it. Similarly, “verbatim” must specify characters, UTF-16 code units, or bytes; one source literal cannot necessarily represent every binary value with unchanged contents.

The Java specification confirms the ordering of Unicode translation before later lexical stages. The Go specification confirms both the optional source prohibition on NUL and CR removal in existing raw-string values. These are material pipeline constraints, not merely aesthetic quoting differences. Sources checked on 2026-11-08: [JLS §3](https://docs.oracle.com/en/java/javase/26/docs/specs/jls/jls-3.html), [Go specification](https://go.dev/ref/spec). The proposal may intentionally change these rules; it needs to say exactly which phase changes.

**Artifact-supported finding: meaningful implementation exists, successful deployment unverified.** `go/toolchain/matchertext.patch` modifies the compiler scanner, public scanner, source lookahead, and constant construction. This is a much better compiler case study than the paper's current implementation section advertises: `doc/impl.tex:1`–`5` names only Scheme and MinML. The patch also correctly notices that Go permits an import alias adjacent to a quote (`go/toolchain/matchertext.patch:9`–`12`), contrary to the appendix's blanket rationale that Go rejects an identifier before a quote. Its narrower recognition condition protects that example. The actual rewriter excludes imports, struct tags, and cgo files because some paths unquote directly. These exceptions reveal the full scope of integration.

There is a three-stage experiment harness (`go/toolchain/experiment.sh`) and acceptance-test input covering literal values, nested pairs, multiline text, and an adjacent import alias. I inspected their source only. A patch and harness are not demonstrated passing compiler tests, unchanged baseline behavior, or successful repository migrations. The patch retains the existing character-reader paths; I have not established that it suspends every NUL/BOM/encoding restriction required by the paper's universal contract.

**Consequence.** Reviewers cannot yet tell whether this is a language-independent mechanism with one realistic deployment, or a family of proposals each requiring unreported exceptions. The existing artifact offers an unusually efficient opportunity to answer that question.

**Concrete repair.** Add one compact implementation case study for Go with a phase table: entry point, transformations bypassed, unchanged transformations, accepted character domain, constant semantics, and unsupported contexts. Run and report the harness on pinned repositories with passing baseline tests, preserving the actual rewritten counts and rejection reasons. Compare stock compiler/original sources, patched compiler/original sources, and patched compiler/rewritten sources. Include scanner/parser/constant/type-checker/formatter behavior and at least one source-to-source tool. For Java and C/C++, provide a clearly labeled design analysis rather than implying their implementation has been completed. A phase trace for one raw `\u005D` sequence inside a Java matchertext literal would make the central requirement concrete.

**Acceptance criterion.** The paper establishes one end-to-end mainstream host whose chosen contract survives the full intended path, and lists the remaining restrictions honestly. Legacy compatibility examples include import aliases and macro/prefix collisions. Every claimed successful run has a pinned version, command, input revision, outcome, and retained log. Other languages' feasibility claims identify the required early lexical changes instead of appealing solely to the BNF.

### 3. Fragment compliance is being used as whole-source compliance and adoption cost

**Exact paper locations:** `doc/eval.tex:77`–`85` names 86.77% as file compliance and explains it as unmatched matchers anywhere in a file; `doc/eval.tex:316`–`325` concludes that adoption cost is small. `doc/appendix/grammar.tex:147` onward already acknowledges structural exceptions such as preprocessing and digraphs.

**Paper-only concern.** High compliance of individual string bodies is useful evidence for adding a host literal. It is weaker evidence that a source language or repository is readily embeddable. Character literals, comments, conditional compilation, macros, generated code, and lexical transformations matter when embedding whole source files. There are also two different adoption tasks: using new host literals, versus making one's source suitable as guest matchertext. The first should not be charged for changing unrelated legacy comments, and the second cannot be evaluated by strings alone.

**Artifact-supported finding: demonstrated operational mismatch.** `LLVM/src/Parser.cpp:405`–`448` extracts string literals and comments, not the entire source or character constants. `:458`–`505` computes file failure by summing the failures of these fragments. That measures “all extracted fragments are individually compliant.” It is not `Verify(original file)`.

Two analytical counterexamples show why neither implication holds. A C file with only `char c = '[';` has no offending extracted string/comment body, but its raw source is not matchertext. Conversely, two source string bodies `"["` and `"]"` can each fail while their surrounding complete source is balanced. Macro fragments and unmatched preprocessor alternatives create further differences. These are logical counterexamples, not executed corpus examples; the prevalence and numerical effect remain unknown.

**Consequence.** The file percentage should not be read as the proportion of source files already eligible for verbatim embedding. Nor do percentages dominated by bracket-free strings establish the effort of adapting the problematic, structurally rich content that motivates the work.

**Concrete repair.** Rename the existing file metric precisely. Add a direct whole-source scan, retaining per-fragment results as a separate measure useful for local migration. Report failures by character literals, comments, strings, and outside opaque text on a modest annotated sample. Distinguish raw-file conformance from post-preprocessing or decoded-token conformance. Measure migration edits and excluded contexts on the Go case study, and show an important embedded-language subset rather than relying only on global sample volume.

**Acceptance criterion.** The two counterexamples get the expected distinct classifications, all tables say which representation is scanned, and no adoption claim confuses a fragment property with a raw-source property. At least one measured migration reports actual converted values and necessary manual repairs, not just theoretical eligibility.

## Additional actionable findings

### Clarify the trusted boundary in the operational theorem

`doc/design.tex:268`–`272` calls the depth counter equivalent to the typed stack. They are equivalent for locating a boundary **conditional on valid matchertext**, not for validating arbitrary input. A depth-only counter accepts a zero-depth prefix such as `([)]` that the typed stack must reject. State that untrusted input requires the typed stack or prior validation, and that the host checks the expected closing matcher and delimiter suffix after finding the boundary. This is a writing correction rather than evidence against the balanced-prefix theorem.

The Lean sources inspected align with the abstract closure/boundary statements; a textual search did not find `sorry` or `admit`. I did not run Lean, validate the trusted environment, or verify the concrete scanners against the proof. Avoid describing the Lean result as a verified implementation of the compiler pipeline or the empirical analyzer. The abstract pair relation also permits multiple openers for one closer or vice versa; the standard three-pair configuration has no such issue, but any generic scanner correctness claim should state the computational/decidability assumptions it needs.

### Recover the incremental-tooling contribution from the artifact

`doc/impl.tex:82`–`89` lists many editors, but editor count is less informative than a representative editing task. The LSP has local-reparse machinery (`go/markup/minml/lsp/reparse.go`); this could support a small but compelling experiment: remove one opener, insert a wrong-kind closer, edit a delimiter, and restore the file. Report diagnostic location, amount reparsed, and whether later syntax remains usable. Compare fresh and incremental parses after the same edits.

There is also a documented, concrete limitation: `dev/README.md:125`–`129` says Zed's block-comment toggle treats the first `]` as the terminator, corrupting or failing to uncomment nested content. This is not evidence that the core language server is wrong; it is evidence that generic editor support does not automatically respect the discipline. Use the case to explain migration/tooling cost and fix or document the operation. Test nested comment toggling and bracket navigation in one supported editor instead of using the list as a usability proxy.

### Tighten the source-encoding contract

`doc/design.tex:282`–`289` is correct that the mathematical predicate is over characters, but overstates what follows for implementations. The Go core parser is byte-oriented (`go/matchertext/parse.go`), which works for detecting these ASCII bytes in valid UTF-8; it does not itself validate Unicode or transparently support arbitrary encodings. Specify Unicode scalar values versus surrogate code units, valid UTF-8 versus arbitrary byte strings, leading/embedded BOM, NUL, CRLF, and normalization. These do not all require new features. A clearly bounded contract is preferable to an implicit universal one. Include a small character-domain test matrix for the supported host.

### Audit lexical extraction and avoid saying “all forms” without coverage evidence

`doc/eval.tex:21`–`26` makes a broad completeness claim. The C/C++ producer reads one token ahead after each literal (`LLVM/src/Parser.cpp:429`–`442`), assigns it to `tok`, then continues to an outer loop that immediately lexes again (`:401`). By static control-flow inspection, a comment immediately following a literal appears to be dropped; I did not execute a reproducer. Add a fixture `"x" /* [ */` and compare the actual token/sample stream to the expected one. Also test concatenation separated by comments, wide/UTF literals, malformed files, preprocessor-disabled regions, and interpolation fragments. Report extraction error rates and deduplication policy; a corpus this large can multiply a small systematic bias.

### Strengthen the comparison with existing raw strings

The formal distinction from adaptive delimiters is genuine, but the ordinary escape reduction is mostly shared with raw strings. Report how often a fixed default raw form fails, how often choosing a different delimiter fixes it, and how often matchertext alone admits a stable fixed hole. The existing `rawHolds`/`mHolds` machinery is a useful starting point after fixing its semantic representation. Include literal byte length and delimiter-selection effort alongside backslash count. For language ecosystems without a raw form, separate that baseline limitation from the benefit specifically due to balancing all three pairs.

### Keep security claims at the actual lexical interface

The receiving-SQL matcher-literal condition at `doc/appendix/string_interpolation.tex:118`–`125` is an important qualification. Promote it wherever the text says a language-independent check suffices, especially `doc/design.tex:245`–`248` and related work. Balanced text inserted into an ordinary SQL quoted literal is not protected merely because the host template validates brackets: an apostrophe has no matchers. The paper now gives the right condition in the appendix; the repair is to make it impossible to miss. Explain that lexical containment does not make arbitrary guest code safe or enforce a URL/HTML/SQL semantic policy.

The proposed silent U+FFFD fallback (`doc/appendix/string_interpolation.tex:145`–`158`) is unnecessary to the main contribution and creates unproven semantic claims about nearly every language. Prefer explicit failure as the specified default. If replacement is retained as an application policy, describe data loss and leave its security properties to the receiving context.

### Reduce speculative breadth and make conservativity language-specific

The URI/MRI and regular-expression appendices are interesting future design sketches, but unsupported ecosystem changes should not compete with one convincing host implementation. The regex class proposals explicitly change accepted meanings, which is honest; do not collectively advertise every extension as conservative. For URIs, an old-valid-input argument is not a complete rollout argument across parsers, proxies, signature/canonicalization layers, browsers, and libraries. Defer deployment claims or offer one round-trip converter with an explicit normalized value model. The paper does not need to standardize new URI syntax to establish the matchertext interface.

## Overall judgment after targeted artifact inspection

The artifact improves my view of the engineering potential: there is already a mainstream-host patch, a conservative migration tool, a useful experiment scaffold, and meaningful editor infrastructure. The paper is underselling that work while overselling what its aggregate metric and generic grammar establish. My provisional assessment remains **weak reject in the present form**, with medium-high confidence in the identified spec/implementation mismatches and medium confidence in the final venue judgment. A corrected semantic evaluation plus demonstrated Go compatibility/migration results would materially change the assessment. The right next version is a sharper practical language-design paper whose abstraction, representation contract, and real toolchain evidence reinforce each other.
