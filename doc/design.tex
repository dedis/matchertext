\section{Matchertext design and rationale}
\label{sec:design}

This section first defines matchertext 
as an abstract mathematical syntax in \cref{sec:design:abstract},
then in \cref{sec:design:concrete}
as a concrete syntactic discipline
pragmatically inspired by predominant practices.
These definitions represent the ``core'' of the matchertext concept,
and are the \emph{only} rules
that different languages must ``agree on''
in order to achieve the main goal of escapeless interlanguage embedding.

\subsection{Abstract definition of matchertext}
\label{sec:design:abstract}

We first define \emph{abstract matchertext}
in order to ensure that the basic concept is clear and precise.

We assume at the outset we are given some arbitrary alphabet $\Sigma$,
along with some finite set $\Pi$ of character pairs 
$\{(o_1,c_1),\dots,(o_k,c_k)\}$,
such that $\{o_i, c_i\} \subseteq \Sigma$ for all $1 \le i \le k$.
We define the \emph{openers} $O$ as the set of characters $o$
such that some pair $(o, c) \in \Pi$.
Similarly, the \emph{closers} $C$ are the characters $c$
such that some pair $(o, c) \in \Pi$.
We assume and require that the sets of openers and closers do not overlap:
\ie $O \cap C = \emptyset$.
We define the \emph{matchers} $M$ as the set of all openers and closers
(\ie $M = O \cup C$).
We define the \emph{nonmatchers} $N$ as
all characters that are not matchers
(\ie $N = \Sigma \setminus M$).
A \emph{matchertext configuration}
is a pair $(\Sigma, \Pi)$ following the above rules.

We now define the language $L$ of \emph{matchertext strings}
inductively (\ie generatively) as follows:
\begin{itemize}
\item	Any string $n$ consisting exclusively of nonmatcher characters in $N$,
	including the empty string,
	is a matchertext string in $L$.
\item	For any matchertext strings $m_1,m_2,m_3$ in $L$,
	and for any pair $(o,c) \in \Pi$,
	the concatenation $m_1||o||m_2||c||m_3$
	is also a matchertext string in $L$.
\end{itemize}

Formally, $L$ is the \emph{Dyck Language}~\cite{chomsky63algebraic} over $\Pi$ where the nonmatchers are classified
as neutral symbols. Equivalently, a string is matchertext if and only if it becomes a Dyck word once all the
nonmatchers are removed from it. With $|\Pi| = 1$ this is the language of balanced parentheses.

Intuitively, this definition captures the basic rule
that \emph{matchers must match} in matchertext.
Openers can be introduced into valid matchertext
only when paired with a matching closer, and vice versa,
but nonmatchers may be interspersed throughout with no constraints.

Matchertext is a purely syntactic rule.
We call it a \emph{syntactic discipline} rather than a language
because it assigns no meaning to the strings in $L$
and no structure beyond the rule that matchers must match;
each matchertext-aware language defines
the meaning of all characters, matchers and nonmatchers alike.

\subsubsection{Escapeless embedding in matchertext}
\label{sec:design:abstract:embed}

Suppose there is a set of languages $\mathcal{L} = \{L_1,\dots,L_k\}$
whose members all agree on a common  matchertext configuration $(\Sigma,\Pi)$.
Any language $L_h \in \mathcal{L}$ can \emph{host}
embedded strings in any other language $L_e \in \mathcal{L}$
without escaping or other transformations to the strings from $L_e$,
provided $L_h$ enforces the following simple \emph{embedding rule}.
Any embedded matchertext string $m \in L_e$ 
must be delimited (surrounded) by
some pair of strings $s_o, s_c$ defined by the host language $L_h$,
such that the full embedding sequence is $s_o || m || s_c$ in $L_h$.
Further, $s_o$ must contain one or more open matchers in $O$
that would be unmatched in $s_o$ alone --
that is, $s_o$ alone \emph{cannot} be valid matchertext --
and $s_c$ must contain one or more corresponding close matchers in $C$
that would be unmatched in $s_c$ alone.

This embedding rule permits escapeless embedding
because no fixed characters or strings, including $s_o$ and $s_c$,
need be unconditionally forbidden in the embedded string $m \in L_e$,
provided that $m$ is valid matchertext.
The host language processor need not know anything
about the embedded language $L_e$ other than that $m$ is matchertext.
A host language processor that parses left-to-right from $s_o$
can ignore any embedded instances of $s_o$ and $s_c$ within $m$
because the matchers they contain must match within $m$.
The host language processor can unambiguously recognize
the closer string $s_c$ that terminates the embedding
because it contains at least one close matcher
that would be unmatched, and thus illegal, if it were part of $m$.

To guarantee that verbatim embedding always works,
a host language \emph{must not} apply
transformations (\eg escapes)
or restrictions (\eg forbidden characters or sequences)
within the embedded matchertext.
Exceptions to this rule (\cref{app:concrete:variations})
reduce verbatim embedding compatibility.


\subsubsection{A formal guarantee of embeddability}
\label{sec:design:abstract:formal}

The reasoning above can be proven with the \href{https://lean-lang.org}{Lean~4} proof assistant
using its \href{https://leanprover-community.github.io}{Mathlib} library,
included in the \texttt{lean} directory of the supplementary material.\footnote{%
	The development relies only on the standard axioms
	\texttt{propext} and \texttt{Quot.sound},
	plus \texttt{Classical.choice} for \cref{thm:design:findend}.}
\Cref{app:lean,app:boundary} reproduce the complete specifications
the theorems are stated against.
We summarize the result here;
it concerns the abstract matchertext language $L$
defined inductively in \cref{sec:design:abstract}.
Two closure properties of $L$ do the work:

\begin{lemma}[Concatenation closure]
\label{lem:design:concat}
If $a \in L$ and $b \in L$, then $a || b \in L$.
\end{lemma}

\begin{lemma}[Wrapping]
\label{lem:design:wrap}
If $m \in L$ and $(o,c) \in \Pi$, then $o||m||c \in L$.
\end{lemma}

\Cref{app:lean} gives proof sketches of both lemmas.

To capture exactly which delimiter strings $s_o,s_c$
the embedding rule of \cref{sec:design:abstract:embed} admits,
we define a \emph{matched delimiter pair} inductively:

\begin{definition}[Matched delimiter pair]
\label{def:design:delim}
The pair $(s_o,s_c)$ is \emph{matched} if it can be formed by these rules:
\begin{itemize}
\item	$(\epsilon,\epsilon)$ is matched;
\item	if $(s_o,s_c)$ is matched and $(o,c) \in \Pi$,
	then $(o||s_o,\; s_c||c)$ is matched; and
\item	if $(s_o,s_c)$ is matched and $x \in N$ is a nonmatcher,
	then both $(x||s_o,\;s_c)$ and $(s_o,\;s_c||x)$ are matched.
\end{itemize}
\end{definition}

Intuitively, $s_o$ supplies a sequence of open matchers
and $s_c$ the corresponding close matchers in properly-nested order,
with nonmatcher characters interspersed freely,
exactly the shape of practical delimiters such as
the \texttt{M} and \texttt{"} surrounding the parenthesis
in \verb|M"(|$\dots$\verb|)"|.

\begin{theorem}[Always-embeddability]
\label{thm:design:embed}
If $m \in L$ and $(s_o,s_c)$ is a matched delimiter pair,
then $s_o||m||s_c \in L$.
\end{theorem}

\begin{proof}[Proof sketch]
By induction on the derivation that $(s_o,s_c)$ is matched
(\cref{def:design:delim}).
The base case is $m$ itself.
A matcher step wraps the induction hypothesis
using \cref{lem:design:wrap};
a nonmatcher step prepends or appends a single-character
nonmatcher string (which is in $L$ by the flat rule)
using \cref{lem:design:concat}.
\end{proof}

\Cref{thm:design:embed} establishes the compositional core
of escapeless embedding:
for \emph{any} valid matchertext $m$, with no exceptions,
the delimited result $s_o||m||s_c$ is \emph{itself} valid matchertext.
It can therefore be embedded again, to any depth,
with no escaping and no expansion of the inner string,
the property that distinguishes matchertext
from the quoting and escaping mechanisms surveyed in \cref{sec:bg}.
The complementary claim of \cref{sec:design:abstract:embed},
that a host parser scanning left-to-right can \emph{unambiguously}
locate the terminating $s_c$,
follows from the same balanced structure;
\cref{sec:design:abstract:findend} makes it operational
and \cref{thm:design:findend} mechanizes it.


\subsubsection{Deciding matchertext}
\label{sec:design:abstract:verify}

Whereas \cref{thm:design:embed} shows that embedding \emph{produces}
valid matchertext,
a host language, or a checkpoint guarding against untrusted input
(\cref{sec:bg}),
must also be able to \emph{recognize} it.
Membership in the language $L$ of \cref{sec:design:abstract}
is decided by a single linear scan,
shown as \cref{alg:design:verify}.
The stack holds the openers seen so far that are not yet matched;
each closer must pop the opener of its own pair,
and the string is matchertext exactly when
the scan finishes with an empty stack.

\begin{algorithm}[!b]
\caption{Deciding whether a string $s$ is matchertext.}
\label{alg:design:verify}
\begin{algorithmic}[1]
\Function{Verify}{$s$}
	\State $st \gets$ empty stack \Comment{unmatched openers}
	\For{each character $x$ in $s$}
		\If{$x \in O$} push $x$ onto $st$
		\ElsIf{$x \in C$}
			\State \textbf{if} $st$ is empty \textbf{or} $(\textsc{Top}(st), x) \notin \Pi$
				\textbf{then return} \textsc{false}
			\State pop $st$
		\EndIf
	\EndFor
	\State \Return whether $st$ is empty
\EndFunction
\end{algorithmic}
\end{algorithm}

\begin{theorem}[Correctness of \textsc{Verify}]
\label{thm:design:verify}
For every string $s$,
\cref{alg:design:verify} returns \textsc{true} if and only if $s \in L$.
\end{theorem}

\begin{proof}[Proof sketch]
By induction on the scan, the stack holds exactly the currently unmatched openers,
so \textsc{Verify} rejects exactly the unmatched or mismatched matchers.
\end{proof}

The procedure runs in $O(n)$ time and $O(d)$ space
on an input of length $n$ with maximum nesting depth $d$,
which \cref{sec:eval:nesting} finds is almost always tiny.
This is the concrete basis for the security argument of \cref{sec:bg}:
admitting untrusted embedded content requires only this passive linear check,
rather than a content-modifying transformation
that must anticipate every sequence sensitive to the host language.
It is also exactly the check that our empirical analysis (\cref{sec:eval})
applies to every string literal and comment in the corpus;
dropping the pair-kind test $(\textsc{Top}(st), x) \notin \Pi$
yields the \emph{relaxed} variant reported there,
which tolerates a wrong-kind closer.


\subsubsection{Locating the end of an embedding}
\label{sec:design:abstract:findend}

A host must also find where an embedding $s_o||m||s_c$ ends
without being misled by matchers inside $m$.
Let the \emph{depth} of a string be its number of openers
minus its number of closers.

\begin{theorem}[Embedding boundary]
\label{thm:design:findend}
If $m \in L$ and $c \in C$,
then every prefix of $m$ has depth at least $0$,
$m$ has depth $0$, and $m||c$ has depth $-1$.
\end{theorem}

A host therefore scans the text after $s_o$ with a depth counter
starting at $0$, or equivalently with the stack of \cref{alg:design:verify},
and stops at the first closer that makes the depth negative:
by \cref{thm:design:findend} this is the first closer of $s_c$,
since any nonmatchers of $s_c$ before it have depth $0$.


\subsection{Concrete matchertext in practice}
\label{sec:design:concrete}

The abstract definition applies to any configuration $(\Sigma,\Pi)$,
but escapeless embedding requires a set of languages to agree on one.
We therefore propose a \emph{standard matchertext configuration}
that fits existing practice:
its alphabet $\Sigma$ is the Unicode/UCS character set~\cite{iso10646ucs},
on which machine-readable languages have already converged,
and its matcher pairs $\Pi$ are
the ASCII parentheses \verb|()|,
square brackets \verb|[]|,
and curly braces \verb|{}|.
Matchertext operates on characters,
so the encoding (usually UTF-8) does not matter.

\subsubsection{Standardizing on matcher pairs}
\label{sec:design:concrete:standard}

A particular choice of the matcher pairs $\Pi$ is less obvious, however,
and hence demands more careful justification.
We start by ``deferring to authority'':
namely the authority embodied in
the UCS character set we already chose.
The parentheses, square brackets, and curly braces
are the only characters in the ASCII --
or ``\href{https://www.compart.com/en/unicode/block/U+0000}{Basic Latin}'' -- 
code block that are standardized as members of the
\href{https://www.compart.com/en/unicode/category/Ps}{Open Punctuation (Ps)}
and 
\href{https://www.compart.com/en/unicode/category/Pe}{Close Punctuation (Pe)}
character classes.
Exactly as their official names indicate,
these character classes denote characters whose standard purpose
is to serve as open and close punctuation in matched pairs.

\paragraph{Why not the ``angle brackets'' \texttt{<>}?}
Many languages use \verb|<| and \verb|>| in pairs,
for generic types in C++ and Java or for markup in HTML and XML.
UCS standardizes them, however,
as the less-than and greater-than symbols,
and programs use them unmatched far more often,
as in \verb|if (a < b)|.
Requiring them to match would make inequalities cumbersome
in almost all languages.
Omitting \verb|<>| from $\Pi$ does not prevent their paired use
in specific languages (\cref{sec:host:ml,sec:embed:ml});
it only avoids a universal rule that they must always match.

\paragraph{Why only the ASCII open/close punctuation?}
UCS has much more open and close punctuation,
and \href{https://www.compart.com/en/unicode/category/Pi}{Initial Punctuation (Pi)}
and \href{https://www.compart.com/en/unicode/category/Pf}{Final Punctuation (Pf)}
classes for paired quotation marks (\eg «quote» or “quote”).
Machine-readable syntaxes rarely use them,
partly because most keyboards cannot type them directly.
They also do not occur strictly in pairs:
three left double quotes (U+201C, U+201E, and U+201F)
can match the right double quote U+201D,
depending on culture and typographic style.
Languages may use any UCS punctuation for their own purposes,
but restricting the strictly-matching set $\Pi$
to the ASCII matchers is simplest and safest.

\paragraph{Why all three ASCII matcher pairs?}
All three pairs are used pervasively in different structural roles,
and no principle selects one of them for a global matching role.
Mixing distinct pairs also gives redundancy that localizes errors:
the missing close bracket is easier to find in \verb|[{}([){}]|
than in \verb|[[][[][]]|.
Finally, every host must use some matcher pair
to delimit embedded matchertext (\cref{sec:design:abstract:embed}),
so including all three gives languages a choice of delimiter.
