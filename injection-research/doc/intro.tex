\section{Introduction}
\label{sec:intro}

Software systems often embed one language inside another: a query, some markup,
a document. When the embedded string is untrusted, its boundary with the
surrounding syntax is where injection lives, as a quote closes a SQL literal or an
angle bracket opens an HTML tag.
The accepted best-practice defense escapes, parameterizes, or
sanitizes the untrusted value so it can no longer be read as structure.

These transforms work one context at a time,
which multiplies attack surface.
Each transform is for a single \emph{host language}
(the surrounding language an untrusted value is embedded into)
and a single syntactic position, chosen by hand at each use site,
so securing one context means maintaining a separate defense for every other.
Could we instead defend the structural boundary once,
with a check that does not change with host language or context?

Conventional defenses address the \emph{collision}
between input value and host syntax,
rewriting the value so its characters cannot be confused with
the host language's.
This approach forces each defense to model that syntax: a sanitizer
shadows the host-language parser, and every divergence is a bypass.
The web has no
universal escaper because parse context is per-language and does not
compose~\cite{owasp_xss}.

So we ask:
can one language-independent check replace per-host-language defenses,
what does it guarantee against an adversary
attempting to circumvent this check,
and how much of real injection vulnerabilities could it reach?

\emph{Matchertext} is a syntactic discipline
requiring only that the ASCII matcher pairs \verb|()|,
\verb|[]|, and \verb|{}| must always match in a string.
A companion paper motivates and explores matchertext
for embedding convenience and usability~\cite{matchertext};
this paper focuses on the discipline's security implications.

Matchertext shows promise to address injection attacks across languages
by strengthening the \emph{boundary}
between host language and embedded value.
A host first constrains untrusted values to be matchertext
(escaping unmatched matchers if it must accept arbitrary strings),
then wraps the untrusted value in a matcher pair
and ends it by matcher balance.
Hosted as \verb|WHERE name = M'(|\emph{value}\verb|)'|,
the payload \verb|' OR '1'='1| cannot break out,
since escaping would need an unmatched \verb|)| that is invalid
matchertext.
One matchertext recognizer inspects only the six matcher characters and serves
every host language.

This paper makes four contributions:
\begin{itemize}
\item A security property, \emph{inertness}: a host language's parse does not
	depend on what its \emph{holes} (the matcher-delimited slots for untrusted
	values) contain. A machine-checked Lean proof covers its boundary premise
	(\cref{sec:threat}).
\item Hole forms for SQL, HTML, LDAP, and PDF: reused where a format already reads
	to matcher balance, a bounded parser change elsewhere (\cref{sec:resist}).
\item A reproducible corpus of \dataInjectionCVEs injection CVEs labeled by
	target syntax (\cref{sec:corpus,sec:results,sec:prevent}):
	\dataContainedShare of attacks with a usable payload are contained under the
	threat model, and \dataHostableShare as labeled target a delimitable syntax.
	Execution sinks stay out of reach.
\item Matchertext-aware forks of SQLite and of the parse5 HTML parser, which
	admit no breakout over the recorded SQL and HTML payloads, also when three
	browsers read the served output (\cref{sec:prevent:exec,sec:prevent:html}).
\end{itemize}
