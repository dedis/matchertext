\section{Injection resistance by matcher-delimiting untrusted input}
\label{sec:resist}

\subsection{Preventing SQL injection}
\label{sec:resist:sql}

In the classic vulnerability, a server composes a clause like \verb|"WHERE name = '"+userName+"'"|.
A \verb|userName| containing a quote closes the literal early and appends
attacker-controlled SQL~\cite{clarke12sql}.
The quote ends the literal because SQL scans for it; to the discipline it is a
\emph{nonmatcher}, left unconstrained.
We instead delimit each untrusted value with a matcher pair and have the query
processor treat the content as embedded matchertext.
It ends the value by matcher balance rather than by scanning for a closing quote,
so the clause becomes \verb|WHERE name = M'(|\textit{userName}\verb|)'|; a name
goes in \verb|[|$\dots$\verb|]|.

Concretely, the canonical injection \verb|' OR '1'='1| now fails two ways.
Supplied verbatim it contains no matchers, so it embeds as the literal text
\verb|' OR '1'='1|, its quotes inert because nothing inside the hole
is read as SQL.
When adapted to attack the new delimiters, as in \verb|)' OR 1=1 --|, it carries
an unmatched \verb|)|: \textsc{Verify} rejects it, and \textsc{ToMatchertext}
escapes the \verb|)| to data.
Because the guarantee depends only on the delimiter being a matcher, not on what
the value denotes, it holds wherever untrusted input appears, not only string
values but numbers and even identifiers such as table or column names.
Which tables a caller may name remains an authorization question, distinct from
injection.

Free-form fields, such as a name, a comment, or a search box, may contain
unmatched matchers (\eg a fragment \verb|f(x| or \verb|smile :]|).
Rather than reject them, we pass them through a total encoder
\textsc{ToMatchertext}$(v)$ that escapes the \emph{unmatched} matchers in
$v$~\cite{matchertext}, and decode on read.
Defined on every input, it never rejects. Its escapes are themselves balanced,
so its output is always valid matchertext (\cref{sec:appendix:tomatchertext}).
That is its sole obligation: language-independent, checkable by \textsc{Verify},
and silent about SQL.
An encoder bug whose output is still matchertext yields mis-encoded \emph{data},
not a breakout; a bug in \textsc{Verify} or the host language's locator is a
breakout.

Reading inverts the encoder. An escape \textsc{esc}$(c)$ is a backslash, a tag
(\texttt{o} or \texttt{c}), and a matched pair (\verb|\o()| for \verb|(|,
\verb|\c[]| for \verb|]|). Input already of this shape is escaped too, so it
decodes to itself; other backslashes stay. Then
\textsc{FromMatchertext} scans the balance-delimited region once, mapping each
\textsc{esc}$(c)$ back to its matcher $c$ and copying every other character,
so that $\forall v, \textsc{FromMatchertext}(\textsc{ToMatchertext}(v)) = v$:
\begin{verbatim}
FromMatchertext(m):
  out = []; i = 0
  while i < |m|:
    if m[i..] begins with esc(c):
      out += c;    i += |esc(c)|
    else:
      out += m[i]; i += 1
  return out
\end{verbatim}
This round-trip is a data-fidelity property that we do not prove: it is
no part of the inertness claim, which rests only on output $\in L$
(\cref{sec:appendix:tomatchertext}).
A decoder bug only corrupts a value: the region is delimited before decoding
begins.
Holes in a statement stored in the schema are rewritten to stock syntax, so
that a stock build can read the database.

Under a matchertext-aware host language that ends each value by matcher balance,
matchertext offers a \emph{structural} property: no valid-matchertext value,
in any position, can escape its delimiters or alter the surrounding query
structure, closing off the sub-class of injection that depends on breaking out
of a delimiter. This guarantee is the inertness of \cref{sec:threat}. It does not by itself
establish that later decoding, reparsing, or execution of the contained value
is safe.

\subsection{Cross-site scripting across HTML contexts}
\label{sec:resist:xss}

The same discipline addresses cross-site scripting across three
injection sites, each with its own escaping regime.
A value placed as element content, between \verb|<div>| and \verb|</div>|, breaks
out on \verb|<| or \verb|&|.
The same value in a quoted attribute, \verb|<input value="|\emph{v}\verb|">|,
breaks out on the active quote rather than \verb|<|, and in an unquoted attribute
the breakout set widens to whitespace and \verb|=|.
A value in a script body, \verb|<script>var n="|\emph{v}\verb|"</script>|, has two
independent exits: the JavaScript string quote and the raw \verb|</script>|
sequence that ends the element regardless of JavaScript syntax.
The recurring bug is applying one escaper, usually HTML-entity encoding, in all
contexts; it fails in single-quoted and unquoted attributes
(\cref{sec:prevent:html}).

Matcher-delimiting collapses the three to a single discipline, as for
SQL.
Each hole is read verbatim up to a matched close bracket and the host language performs no
transformation, using matchertext markup forms~\cite{matchertext}
(\eg \verb|<div [|\emph{v}\verb|]>|, \verb|value=[|\emph{v}\verb|]|, and
\verb|<![MDATA[|\emph{v}\verb|]]>|, a CDATA-like section read to matcher balance).
Because the matchers are \verb|()[]{}| and not \verb|<>|, the characters that
drove every breakout above, \verb|<|, \verb|&|, the quote, and even the literal
\verb|</script>| sequence, become ordinary data inside a matched hole.
The parser counts brackets rather than scanning for tags, so an injected
\verb|<img src=x onerror=steal()>| is inert text.
The three context-specific sanitizers thus reduce to the single \textsc{Verify}
recognizer, the same one used for SQL, which rejects only an unmatched
matcher or nesting deeper than $D$.

The guarantee covers one host language: in a \verb|script| or \verb|style|
body a hole stops the end tag, not the JavaScript or CSS inside
(\cref{sec:prevent:html}). It stops at sinks that execute their contents by design: a payload kept dutifully inside \verb|<a href=[|\emph{v}\verb|]>| stays within the
attribute yet still runs when \emph{v} is a \verb|javascript:| URL, because that
is an execution context, not a structural breakout; an \verb|onerror| handler is
the same.
Such semantic sinks are out of scope.
A second limit is expressiveness: matchertext content is verbatim text and cannot
carry child markup.
This restriction suits embedding an untrusted string as inert data but is not
a substitute for rendering a user's rich HTML, a harder problem left to
allow-list sanitizers.
The clean guarantee covers the data-not-markup case; the \dataDocumentCVEs XSS
CVEs whose attacker uploads a whole document get no hole (A2).

\subsection{Preventing LDAP injection}
\label{sec:resist:ldap}

LDAP needs no new hosting form, because a search filter already delimits each
assertion with a matcher.
In the bind check
\verb|(&(uid=|\textit{userName}\verb|)(userPassword=|\textit{pass}\verb|))|, the
classic attack~\cite{alonso08ldap} is a \verb|userName| such as \verb|*)(uid=*|
that closes its assertion early, so the password clause no longer constrains the
bind.
A filter parser that ends the value by matcher balance rather than at the first
\verb|)| defeats it as for SQL: the payload carries an unmatched \verb|)|, so
\textsc{Verify} rejects it and the encoder escapes it to data. That reading rule is a parser change:
stock parsers stop at the first \verb|)|, and RFC~4515 escapes every
parenthesis~\cite{rfc4515}.

\subsection{Preventing PDF object injection}
\label{sec:resist:pdf}

PDF's literal strings are parenthesis-delimited and admit \emph{balanced}
parentheses unescaped~\cite{iso32000}, so the format already mandates matcher
balance.
Yet a generator that concatenates untrusted input into a
\verb|(|$\dots$\verb|)| string or a \verb|/URI| or \verb|/JS| action lets the
attacker close the string and append objects the viewer parses and runs.
This is the ``XSS for PDFs'' class~\cite{heyes20pdf}.
Emitting the value through \textsc{ToMatchertext} escapes the canonical breakout
\verb|)>>/AA<<|$\dots$\verb|(|, which begins with an unmatched \verb|)|, to inert
data, and a balanced \verb|f(x)| embeds unchanged.
PDF alone breaks A3: its reader skips an escaped \verb|\(| when counting, so a
value balanced for \textsc{Verify} can still close the string; PDF's own
backslash escaping, a host-specific step, closes this.
As before, data an application deliberately routes into a \verb|/JS| action still
runs but can no longer escape its string to \emph{introduce} one.

Adoption is two problems, not one, and the hosting syntaxes
of~\cite{matchertext} answer only the second.
Assumption A1 of \cref{sec:threat} constrains the \emph{host language}: the SQL engine, HTML
parser, or directory server that interprets the composed text must end the
embedded value by matcher balance.
Assumption A2 constrains the \emph{application} that composes it: the untrusted value
must reach a matcher-delimited hole rather than be concatenated in beside one.
The two are met by changes to different languages, by different people,
and are worth separating.

\paragraph{Making the host language aware (A1)}
\Cref{tab:resist:a1} compares the routes.
Reusing a construct the format \emph{already} reads to matcher balance needs no
new syntax:
PDF literal strings (\cref{sec:resist:pdf}) cost no new syntax, though A3 needs
PDF's own backslash escaping; LDAP filters (\cref{sec:resist:ldap}) keep their syntax but need a
balance-reading parser.
But this route reaches only the formats built that way.
Extending a host language's grammar with a hole form reaches the syntaxes where injection
actually concentrates, at the price of a change inside the host language's parser.
The change is not always conservative: T-SQL already gives
\verb|[|$\dots$\verb|]| a meaning as a delimited identifier.
A hole form for SQL must either pick different delimiters or accept that
existing code changes meaning, unlike the \verb|M"|$\dots$\verb|"| literal
of~\cite{matchertext}, a C string literal read to matcher balance, for C.
Our SQLite fork accepts this for \verb|[|$\dots$\verb|]| names and
\verb|SELECT m'(x)'| (\cref{sec:appendix:systems}).
Replacing the host language obtains A1 by construction and reaches everything it
covers, but only for new deployments, since nothing previously written parses.


\paragraph{Making the composition safe (A2)}
A1 is worth nothing if the value never reaches the hole, and today that is left to
developer discipline: nothing stops a programmer from concatenating into the query
around a hole rather than into it.
This is where the source-level syntaxes of~\cite{matchertext} earn their place in
a security argument, and \cref{tab:resist:a2} sets them against the status quo.
A matchertext literal with structural interpolation, \verb|M{}"|$\dots$\verb|"|
with \verb|{|$v$\verb|}| holes, makes the template's holes
explicit and its structure fixed, so an interpolated value cannot alter the
surrounding query no matter what it contains.
This is an application of the discipline that~\cite{matchertext} identifies as its
security-relevant use of interpolation.
In C-like languages a marker abutting a quote is a syntax error outside
macros, so the literal form keeps existing code.


Together the two assumptions replace an obligation on the programmer at every use
site with an obligation on two parsers: A1 changes a bounded part of the host language's
parser, and A2 adds a lexical form to the application language.
Neither removes a parser from the trusted base, and neither is meant to.
