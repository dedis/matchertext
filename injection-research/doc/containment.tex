\section{Measuring matchertext containment}
\label{sec:prevent}

Matchertext contains an injection under two conditions. First, the untrusted
value lands in a slot a matchertext-aware host delimits with a matcher pair.
Second, the value is itself valid matchertext, checked by the passive
\textsc{Verify} scan rather than by escaping.
An attack then fails one of two ways: by \emph{inert embedding} or by
\emph{rejection}.
Which route a real attack takes is a property of the payload, and so measurable
against the corpus.

\paragraph{Method.}
For each of the \dataPayloadBackedCVEs payload-backed CVEs we reuse its syntactic skeleton and decide two things:
whether the target syntax is one a matchertext host can delimit with a matcher
pair, and, if so, whether the skeleton passes \textsc{Verify}.
A passing skeleton is contained by \emph{inert embedding}; a failing one is
stopped by \emph{rejection}.
This test simulates each recorded payload under a matchertext-aware host.
It then exercises a deployed host parser on the same payloads, for the one
syntax a matchertext host now implements.

\paragraph{Results.}
Of the \dataPayloadBackedCVEs payload-backed injection CVEs, the recorded
payloads of \textbf{\dataContained} (\textbf{\dataContainedShare}) are contained
by a matcher-delimited slot that a matchertext-aware host reads to matcher
balance, assuming no intervening decoding.
The split between the two mechanisms turns on the host's native delimiter, and
the per-syntax mechanisms of \cref{sec:resist} appear directly in the corpus.
LDAP is the pure rejection case: every real LDAP payload fails \textsc{Verify}
(\dataLdapInert inert, \dataLdapRejected rejected), its parenthesis breakout
carrying an unmatched \verb|)|.
SQL and XSS break out on nonmatchers, so they are overwhelmingly valid
matchertext and embed inertly.
The \dataSqlRejected SQL rejections additionally carry an unbalanced function or
subquery parenthesis.
The ratio between the two mechanisms is descriptive, not predictive.
These payloads were written against quote and tag-delimited hosts.
An attacker aware of a matcher-delimited slot would balance the matchers,
shifting cases from rejection to inert embedding.
Containment is unaffected, since both routes hold the value.
The split itself is a property of the recorded corpus rather than of an adaptive
attacker.

\paragraph{Where matchertext cannot help.}
The remaining \dataOutsideCVEs payload-backed CVEs are outside both conditions, and divide
by the premise of \cref{sec:threat} they fail.
\dataOutsideSemantic target execution/semantic sinks (server-side templates, expression
languages, code evaluation, spreadsheet formulas, and \verb|javascript:| URLs)
where the host runs the contained value by design. Delimiting cannot stop
it: the template payload \verb|{{7*7}}| is already valid matchertext yet is
still executed.
The other \dataOutsideNonmatcher target contexts delimited by non-matchers with no matcher hosting:
shell command separators (\verb|;|~\verb-|-~\verb|&|), CR/LF header breaks, and
the angle brackets of XML/XXE, none of which are matcher characters.

\paragraph{Projection.}
A payload is required to classify the mechanism, but the \emph{context}
condition can be read from the syntax label alone.
Projecting it onto the full corpus, at most \textbf{\dataHostableCVEs} of the
\textbf{\dataInjectionCVEs} injection CVEs (\textbf{\dataHostableShare}) target a matcher-delimitable
syntax.
This is an upper bound, since a fraction of HTML/DOM cases are the
\verb|javascript:| semantic sinks above.
Of the \dataHtmlDomBacked HTML/DOM CVEs carrying a payload, \dataHtmlDomJsSinks
are such sinks, a rate of \textbf{\dataJsSinkRate}.

Turning the measured rate into a corpus estimate needs care, because
payload-backed CVEs are not a random sample.
A SQL payload is a literal string a write-up can quote, whereas code-eval and
argument payloads are built at run time and never appear verbatim.
So payload availability correlates with matcher-hostable syntax.
Applying the pooled \dataContainedShare wholesale inherits that skew: it yields
\dataNaiveEstimate (\dataNaiveShare), too high by \dataSkewCost CVEs.
Estimating per syntax and weighting by the corpus counts (\cref{tab:strata}) is
the standard post-stratification correction, and gives a central estimate of
\textbf{\dataCentralEstimate} (\textbf{\dataCentralShare}) against the
\dataHostableShare ceiling.
Within a syntax the estimate still assumes payload-backed CVEs carry semantic
sinks at the same rate as the rest.

contained share \emph{within} the payload-backed subset.

\paragraph{What payload availability bounds.}
The gap between \dataPayloadBackedCVEs and \dataInjectionCVEs is payload
availability, a property of the disclosure ecosystem, not a containment failure.
Mandiant finds \textbf{51\%} of vulnerabilities disclosed in 2021--2022
eventually acquired public exploit or proof-of-concept
code~\cite{mandiant23tte}. VulnCheck reports \textbf{26\%} for CVEs carrying
2025 identifiers~\cite{vulncheck26exploit}. Our own corpus is stricter: \dataInjectionWithPoc of our
injection CVEs (\dataInjectionWithPocShare) carry any proof-of-concept reference
at all, a literal attack string being a stricter requirement still.
The measurable population is therefore roughly half the corpus, and the
fragment-level bound should be read against that population, not against
\dataInjectionCVEs.

\subsection{An executed host}
\label{sec:prevent:exec}

The measurement above is a simulation: it runs \textsc{Verify} over a syntactic
skeleton, never a payload through a parser.
\Cref{sec:threat} names the two obligations a simulation cannot reach, parse
inertness (L2) and interpreter inertness (L3), as per-host and left to
implementation.
We test them for one host, a matchertext-aware
SQLite,\footnote{The fork and the driver of this experiment are available in
an anonymized repository: \url{https://anonymous.4open.science/r/matchertext-sqlite-4301/}.} over the CVE-derived SQL
subset and the standalone SQL payload corpora.

\paragraph{The deployed host.}
The build realizes the discipline of \cref{sec:resist} directly: a value is
placed in the SQL text inside an \verb|M'(...)'| literal, an identifier inside
\verb|[|$\dots$\verb|]| read to matcher balance (A1), and the statement is
prepared through the ordinary interface.
The matcher-delimited hole is offered beside legacy composition rather than
replacing it, so existing SQL keeps working and adoption is incremental. This is
the point-of-use character of A2: a value the caller still concatenates
into host syntax is unprotected. This holds exactly as with an escape or a bound
parameter.
An opt-in strict mode additionally refuses the legacy prepare entry points,
turning A2 from a convention into an enforced invariant for callers who want it;
the measurement below reports the additive default and this strict build side by
side.

\paragraph{Method.}
Each of the \dataSqliPayloads distinct SQL payloads (\dataSqliFamilies families)
is placed through every compatible hole-arm pair and compared against the same
hole holding a benign value.
The 16 fixtures cover single- and double-quoted text, raw and parenthesized
numbers, \texttt{IN} lists, \texttt{ORDER BY} and \texttt{LIMIT} expressions,
one- to four-column selects, one- and two-column inserts, and identifier
positions.
Hosts and arms are each typed by hole kind, so \dataSqliValueHosts value
fixtures run against \dataSqliValueArms value arms and \dataSqliIdentHosts
identifier fixtures against \dataSqliIdentArms identifier arms:
\dataSqliCasesPerPayload cases per payload, \dataSqliCases in all.
The two typed strict entry points are swept separately and reported in the
right-hand block.
The \dataSqliIdentMtMalformed name-hole cases that do not compile are the
\dataSqliNulPayloads payloads carrying a trailing zero byte, which ends a
SQLite statement wherever it appears, so the composed statement is never
reached rather than the hole failing to contain it.
The set retains every recorded payload.
SQLite variants are limited to one transport percent-decoding pass, SQL Server
\verb|N'...'| text, PostgreSQL dollar-quoted text, and a terminal MySQL
\verb|#| comment.
No function, operator, query, or attack objective is changed.
The oracle is the compiled statement, not the string: the \textsc{Explain}
bytecode with the value operand redacted, the read-only flag, whether any SQL is
left after the first statement, and the rows returned, each read against the
benign baseline.
A payload counts against a defense only where the control actually breaks out.
The control is naive concatenation into a quoted or raw value context, or a bare
name. Most recorded payloads are fragments that never parse against SQLite and
are not attacks here.
That effective set is \dataSqliEffective payloads.

\paragraph{Results.}
Over the effective set no matchertext hole admitted a breakout (\cref{tab:sqli}):
\dataSqliMtBreakout through the \verb|M'(...)'| value hole, \dataSqliMtStrictBreakout
through the verify-then-embed route, and \dataSqliIdentMtBreakout through the
\verb|[|$\dots$\verb|]| name hole.
The legacy value defenses hold as well, \texttt{\%Q} and \texttt{\%q} escaping
and a bound parameter, which is the honest baseline.
Concatenation is the contrast: \dataSqliConcatBreakout breakouts of the value
control and \dataSqliIdentConcatBreakout of the identifier control, on the very
same payloads.
That breakout is available only because the additive build leaves legacy
composition open.
Recompiled in the opt-in strict mode, every text-splicing prepare, the
concatenation and the in-band \verb|M'(...)'| alike, is refused before it reaches
the parser (\cref{tab:sqli}, right). So the \dataSqliEffective effective-set
attacks have no path at all, and A2 holds by construction rather than by
discipline.
The only admitted paths are then the typed \texttt{?V} value and \texttt{?I}
identifier parameters of \texttt{sqlite3\_matchertext\_prepare\_v3()}. Run
over the SQL corpus they contain it exactly as the additive holes do:
\dataSqliStrictValueBreakout value breakouts and \dataSqliStrictIdentBreakout
identifier breakouts. The \texttt{?V} route binds each valid value and refuses
the \dataSqliStrictValueRejected that are not matchertext, and the \texttt{?I} route
holds each as a single name.
Short of strict mode, an application closes the same gap itself by carrying the
two \textsc{Verify} checks of the discipline. The first: that the input is valid
matchertext, which admits it or routes it through the encoder. The second: that the
input placed in its matcher-delimited hole leaves the assembled statement valid
matchertext, the closure the host reads to matcher balance.
The value-hole and name-hole rows are exactly those two checks applied by the
driver, and the concatenation control is their absence.
The value hole embeds each payload inertly, its quotes and operators read as
data.
The verified route instead refuses the \dataSqliMtStrictRejected payloads that
are not valid matchertext, so the two mechanisms of \cref{sec:resist}, inert
embedding and rejection, appear directly.
The identifier hole holds each payload as a single name, which resolves or does
not but never contributes syntax, and is the one position a bound parameter
cannot fill.

\paragraph{Falsifiability.}
A zero is evidence only if the oracle could have reported a one.
We rebuild the scanner deliberately broken, once so the boundary locator stops
at the first closer and once so \textsc{Verify} always accepts, and rerun.
Each broken build changes the verdict of the holes that rest on it, in up to
\dataSqliSabotageDetect of cases. Those are the value and name holes that end by
matcher balance and the verified route that calls \textsc{Verify}. So the honest
zero is read against demonstrated detection power rather than a blind harness.
The C scanner and an independent implementation agree on \textsc{Verify} for
every payload, and the run is deterministic.
