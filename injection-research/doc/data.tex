\subsection{Data sources}
\label{sec:data}

Every source is keyed on the CVE identifier, so no record is duplicated;
each additional database contributes enrichment or PoC rows rather than a second
copy of the record.
A CVE ID names a record, not a vulnerability: \dataLongDescriptionTwins injection CVEs
repeat another's long description, and at most \dataWordpressCnaRepeats of
\dataWordpressCnaCves WordPress-CNA CVEs repeat another CNA's plugin and version.
All sources are snapshot-pinned by git commit or content hash in a manifest, so
the corpus is reproducible.

\paragraph{Identity and enrichment}
The \href{https://github.com/CVEProject/cvelistV5}{MITRE CVE List}
(\texttt{cvelistV5}) is the canonical record of identity, of the CVE Numbering
Authority (CNA) that assigned it, and of its description.
\href{https://nvd.nist.gov/vuln/data-feeds}{NVD} supplies normalized CWE and CVSS; \href{https://github.com/cisagov/vulnrichment}{CISA Vulnrichment}
backfills recent CWE/CVSS via its Authorized Data Publisher (ADP) container;
\href{https://github.com/cisagov/kev-data}{CISA Known Exploited Vulnerabilities} (KEV) marks known-exploited CVEs;
\href{https://www.first.org/epss/}{FIRST Exploit Prediction Scoring System} (EPSS) supplies exploit-likelihood
scores; and the \href{https://cwe.mitre.org/}{MITRE CWE list} provides the
weakness hierarchy used for classification.
\href{https://github.com/github/advisory-database}{GitHub Security Advisories},
\href{https://access.redhat.com/security/data}{Red~Hat}, and
\href{https://security-tracker.debian.org/tracker/}{Debian} add further CWE,
CVSS, severity, and fix-state signals through their CVE aliases.
Enrichment is kept \emph{source-separated}, each CWE or CVSS row tagged with its
origin rather than merged, preserving provenance and exposing cross-source
disagreement.

\paragraph{Proof-of-concept payloads}
PoC databases supply real attack strings:
\href{https://gitlab.com/exploit-database/exploitdb}{Exploit-DB}, the
\href{https://github.com/projectdiscovery/nuclei-templates}{Nuclei detection
templates}, the
\href{https://github.com/rapid7/metasploit-framework}{Metasploit Framework}
modules, the
\href{https://github.com/nomi-sec/PoC-in-GitHub}{nomi-sec PoC-in-GitHub} index,
the \href{https://github.com/trickest/cve}{trickest/cve} exploit index, and
\href{https://github.com/vulhub/vulhub}{Vulhub}'s reproduction environments.
The first three, Vulhub's worked exploit requests, and six smaller PoC
collections are cloned locally so that a payload can be extracted.
PoC-in-GitHub, trickest, and two similar indexes give links (14 sources in all); a
linked repository is read at a pinned commit, an advisory as a page, keeping only the payload.
For a trickest entry, the candidate exploit repositories and the
researchers' write-ups count as PoC evidence, not the vendor's commits, issues,
and advisories.
References are unified in one table with a local path where a payload is
extractable; because exploit code is dual-use, the corpus stores only links,
identifiers, and locally-extracted fragments, redistributing no exploit files.

\paragraph{Scale}
The pinned snapshot comprises \textbf{\dataCVERecords} CVE records
(\textbf{\dataPublishedCVEs} in the \texttt{PUBLISHED} state).
Across all categories the PoC databases link to \dataPocTrickestCVEs CVEs (trickest),
\dataPocExploitdbCVEs (Exploit-DB), \dataPocGithubCVEs (PoC-in-GitHub), \dataPocNucleiCVEs (Nuclei),
\dataPocMetasploitCVEs (Metasploit), and \dataPocVulhubCVEs (Vulhub). Their
coverage of the injection subset is reported with the results in
\cref{sec:results}.
A key methodological caveat is that these sources have different, sometimes
mutable, update cadences (NVD in particular re-scores CVEs continuously).
The analysis therefore fixes the snapshot of \dataSnapshotDate{} and treats ``field missing in
source'' as distinct from ``property absent in the vulnerability.''
The manifest also pins the forks and tools; git sources, many under restrictive
terms, are not archived but fetched at their pinned commits.
