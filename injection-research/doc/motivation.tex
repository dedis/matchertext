\section{Background and motivation}
\label{sec:motivation}

Injection remains among the most damaging and persistent classes of software
vulnerability. This section surveys the breadth of the problem beyond its most
familiar members, reviews the measured prevalence and cost, then shows why the
very machinery built to contain injection has itself become a recurring source
of vulnerabilities: the motivation for the structural approach this paper evaluates.

\subsection{A wider family of embedding hazards}
\label{sec:bg:hazards}

SQL injection and XSS are only the most familiar members
of a much larger family that share the boundary-crossing cause of \cref{sec:intro}.
The same failure recurs across many more language pairs than those two,
and produces symptoms well beyond information disclosure.

Several are, like SQL injection, outright remote compromises: the 2021
Log4Shell vulnerability expanded a \verb|${jndi:...}| sequence appearing
anywhere in a logged string into a remote lookup that executed
attacker-supplied code~\cite{cve2021log4shell}. Command injection lets
metacharacters such as \verb|;| or \verb|&| in unquoted input break out of a
single shell argument~\cite{owasp_cmdinjection}. Spreadsheet formula injection
turns a CSV field beginning with \verb|=| into code: one Azure activity-log
entry executed on an administrator's machine on download~\cite{gietzen18csv}.
Template injection lets an expression such as \verb|{{7*7}}| reach the
template engine server-side~\cite{portswigger_ssti} or escape the AngularJS
expression sandbox client-side~\cite{peguero16angular}. Even purpose-built
defenses are not immune: the DOMPurify sanitizer has been bypassed by
\emph{mutation} XSS, in which the browser's own parser rewrites
already-sanitized markup back into an executable form~\cite{heyes20mxss}.
Other members corrupt data or deny service rather than disclose it: YAML's
implicit typing (the ``Norway problem'')~\cite{oconnor23yaml},
regular-expression denial of service~\cite{owasp_redos}, and the XML
``billion laughs'' entity expansion~\cite{sullivan09xml}.

Ad-hoc syntactic fixes also tend to backfire: PHP's \verb|magic_quotes|
auto-escaped request data inconsistently, invited double-escaping bugs, and
was deprecated~\cite{php_magicquotes}. What unites the largest of these cases
is structural: content meant to be inert data is read as syntax because a
bracket or quote within it escapes its intended region. Because it recurs
across language pairs, one discipline can address the breakout-based members
at once, distinct from the execution and algorithmic members (template
evaluation, ReDoS, entity expansion) it cannot address.


\subsection{Prevalence, cost, and the sanitizer attack surface}
\label{sec:bg:prevalence}

These failures are neither rare nor fading: injection has appeared in every
edition of the OWASP Top~10 since 2010, subsuming cross-site scripting since
2021~\cite{owasp_top10_2021}, and the underlying weaknesses top MITRE's 2025
CWE Top~25, XSS (CWE-79) first and SQL injection (CWE-89)
second~\cite{cwe_top25_2025}. The volumes are large: OWASP's 2025 Injection
category maps to 62,445 recorded CVEs, more than 30,000 of them XSS and more
than 14,000 SQL injection~\cite{owasp_top10_2025}. Edgescan's 2025 report
attributes 28.28\% of critical and high-severity web and API findings to SQL
injection and a further 17\% to XSS~\cite{edgescan25}. A single failure can be
severe: the 2015 TalkTalk SQL injection exposed the data of over 150,000
customers and drew a regulatory fine~\cite{ico_talktalk}.

More telling is \emph{why} these bugs persist: escaping and context-sensitive
sanitization are empirically error-prone. In one controlled study, all ten
programmers asked to fix an XSS flaw with a standard output-encoding library
failed to remove it completely~\cite{wijayarathna18esapi}. Real PHP
applications carry far more distinct sanitizers than syntactic contexts, one
defining 95 sanitization functions against thousands of output
sites~\cite{weinberger11xss}. A 2024 study of nearly a million GitHub projects
found SQL assembled by string concatenation in 42\% of Java files, 56\% of
C\#, and 91\% of PHP~\cite{dennis24sql}.

\label{sec:bg:sanitizer}%
The sanitizer machinery is itself a recurring source of vulnerabilities.
A production HTML sanitizer must track the host parser's full and quirk-laden
behavior: DOMPurify's core file runs to roughly 2,400 lines and the larger
sanitizers reach tens of thousands project-wide.
Correct only while its model matches every browser exactly, each divergence
becomes a bypass. The bypasses recur as named classes: mutation
XSS~\cite{heiderich13mxss}, parsing differentials~\cite{klein24parsing}, and DOM
clobbering~\cite{khodayari23clobbering}.
The flaws are a steady stream: DOMPurify has carried at least nine CVEs, with
sixteen security advisories in under three months of 2026
alone~\cite{dompurify_advisories}. The Rails HTML sanitizer disclosed five
CVEs on a single day~\cite{rails_sanitizer_cves}.
The point is not that sanitizers are dispensable. It is that a transformation
re-implementing another language's parser, re-synchronized as it changes, is
inherently a large attack surface.

This is the concrete case for preferring a structural \emph{check} to a
structural \emph{transformation}.
Verifying that a value's matchers balance is host-independent and a few lines.
A sanitizer instead must shadow the host parser and its quirks. The security
literature has repeatedly favored safety by construction, typed template
contexts, and parameterized queries over ad-hoc
escaping~\cite{samuel11csas,momot16langsec,owasp_parameterization}.
The check is not the whole trusted base: a matchertext host must also end an
embedded value by matcher balance and suppress its own decoding inside the
hole, and the write path adds an encoder and its inverse (\cref{sec:threat}).
Matchertext thus relocates trust rather than eliminating it: what must hold
uniformly across languages shrinks to a small host-independent check, and what
remains per host is a bounded change to a parser the host already owns.

The defenses of \cref{sec:bg:sanitizer} share a shape: each is written for one
composing language and one host, and works by knowing the host well enough to
transform values for it. A Java-to-SQL escaper knows SQL, and an HTML
sanitizer knows the browser's parser closely enough to predict it. Neither
transfers to the other's problem, so the number of defenses to write, audit,
and re-synchronize grows with the product of the two populations.

\Cref{fig:bg:waist} shows the alternative: a rule that both sides implement
once decouples them, because the rule mentions neither. A language that emits
valid matchertext is compatible with every host that reads to matcher balance.
Such a host accepts values from every such language, without either knowing
what the other is. The count falls from $N \times M$ relationships to $N + M$
implementations. This is the shape the Internet protocol stack takes for the
same reason: a waist thin enough that what sits above and below it can vary
independently.

Whether that shape is worth adopting is a security question rather than an
aesthetic one, and it turns on what the shared rule actually guarantees when the
value in the hole is chosen by an attacker.
